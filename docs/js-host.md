# JavaScript Host Integration & Bundlers

This page details how to execute compiled WebAssembly components inside JavaScript runtimes, covering Node.js native execution, browser native loading (via Import Maps), and configurations for modern bundlers (**Vite** & **Webpack 5**).

---

## 1. Directory Structure

Our JavaScript packages are structured under `bindings/js/` (and `bindings/node/v1/` for the legacy node loader):

```text
bindings/js/
  ├── v0/                              # Pure WASM Browser MVP
  │    ├── index.html                  # Demo container
  │    └── my_lib/
  │         ├── index.js               # Export facade
  │         └── _generated/
  │              ├── loader.js         # Custom loader with MIME-type fallback
  │              └── my_lib_v0.wasm    # Stateless Go WASM binary
  │
  └── v2/                              # WASI Preview 2 Component
       ├── package.json                # Declares @bytecodealliance/preview2-shim dependency
       ├── my_lib/
       │    ├── index.js               # Entry point
       │    ├── geometry.js            # Point / Rectangle class wrappers
       │    ├── store.js               # Stateful KV-Store wrapper
       │    └── _generated/
       │         ├── my_lib_component.js # jco transpiled ES Modules
       │         └── *.wasm            # Go Component binaries
       │
       └── samples/
            ├── esm/                   # Browser integration without bundlers
            ├── vite/                  # Local Vite project integration
            └── webpack/               # Webpack 5 custom configuration
```

## 2. WASI Preview 2 Browser Loading: Import Maps

Transpiled component ES Modules generated by `jco` import system shims (e.g., `import { environment } from '@bytecodealliance/preview2-shim/cli'`). In a pure browser environment, the browser doesn't know where to find `@bytecodealliance/preview2-shim` because there are no local `node_modules` folders.

To resolve this natively in-browser without any build tools, we define a W3C Standard **Import Map**:

```html
<script type="importmap">
{
  "imports": {
    "@bytecodealliance/preview2-shim/cli": "https://esm.sh/@bytecodealliance/preview2-shim/cli",
    "@bytecodealliance/preview2-shim/clocks": "https://esm.sh/@bytecodealliance/preview2-shim/clocks",
    "@bytecodealliance/preview2-shim/filesystem": "https://esm.sh/@bytecodealliance/preview2-shim/filesystem",
    "@bytecodealliance/preview2-shim/io": "https://esm.sh/@bytecodealliance/preview2-shim/io",
    "@bytecodealliance/preview2-shim/random": "https://esm.sh/@bytecodealliance/preview2-shim/random"
  }
}
</script>

<script type="module">
    // Natively imported! Browser downloads shims from CDN dynamically
    import { geometry, KVStore } from './my_lib/index.js';
    
    const db = new KVStore();
    await db.set("user", "gpineda");
</script>
```

## 3. Bundler Configurations

When compiling web applications using build tools, the bundler must resolve the shims and compile the WebAssembly assets.

### A. Vite Integration
Vite resolves local module dependencies out-of-the-box using standard Node module resolution. In our Vite sample [`package.json`](file:///home/gpineda/Documents/ouvrage/labs/wasi-polyglot-bindings-reference/bindings/js/v2/samples/vite/package.json), we link to our library locally:
```json
  "dependencies": {
    "my-lib-v2": "file:../.."
  }
```
Vite resolves the ES Modules and automatically links the browser-compatible shims during development. No custom config is required.

### B. Webpack 5 Integration
Webpack 5 requires explicit configuration to handle WASI components correctly. The configuration file [`webpack.config.js`](file:///home/gpineda/Documents/ouvrage/labs/wasi-polyglot-bindings-reference/bindings/js/v2/samples/webpack/webpack.config.js) must define these rules:

1.  **Enable WebAssembly Experiments**:
    Async WebAssembly loading is disabled by default in Webpack 5. We must enable it along with outputting the bundle as an ES Module:
    ```javascript
      experiments: {
        outputModule: true,
        asyncWebAssembly: true
      }
    ```
2.  **Mock Node System APIs (Fallback)**:
    Because `@bytecodealliance/preview2-shim` references Node-specific filesystems and streams that browsers lack, we configure Webpack to ignore these dependencies when building for the browser:
    ```javascript
      resolve: {
        fallback: {
          fs: false,
          os: false,
          path: false,
          crypto: false,
          stream: false
        }
      }
    ```
3.  **Bypass Node Scheme Imports (`externals`)**:
    Webpack fails when encountering import statements using the `node:` scheme (like `import 'node:fs/promises'`). We mark these imports as **external** so Webpack leaves them intact in the output file (they are never executed by Chrome in our runtime calculation path):
    ```javascript
      externals: {
        'node:fs/promises': 'module node:fs/promises',
        'node:fs': 'module node:fs'
      }
    ```
4.  **Inject script as ES Module**:
    To allow the final bundle to execute modern syntax like `import.meta` (required to resolve WASM relative paths), the generated HTML file must load the bundle script with `type="module"`:
    ```javascript
      plugins: [
        new HtmlWebpackPlugin({
          template: './index.html',
          scriptLoading: 'module' // Forces <script type="module">
        })
      ]
    ```

## 4. Automation Commands

To run tests and demo servers (Vite and Webpack) using our pre-packaged local Node v22:
```bash
# Run Node.js native unit tests (V1 vs V2)
make run-node-v1
make run-node-v2

# Start Vite browser dev server
make run-vite-sample

# Start Webpack 5 browser dev server
make run-webpack-sample
```
